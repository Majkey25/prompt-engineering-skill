# Task contract examples

These are original templates for testing the revised guidance. Replace placeholders with supplied or verified facts. Omit fields that do not help. Do not assume a named app is connected.

## Research artifact

```text
Create a [format and size] draft for [audience] from [source set and relevant period]. Prioritize [decision or questions]. Tie material findings to source evidence, distinguish recommendations, and mark gaps or conflicting claims. Use [supplied template] when available. Before finishing, check that each main finding has support. Return the artifact for review.
```

A polished summary is not the requested artifact. Small samples do not establish population-wide prevalence. Report how themes were counted when frequency affects a decision.

## Project update

```text
Draft a [length] update for [meeting date and audience] using [current plan] and [relevant decisions]. Include progress, open decisions, risks, and next actions. Preserve approved dates and amounts. Each action needs an evidenced owner and due date, or an explicit missing-field marker. Return the draft at the requested review point.
```

Do not satisfy completeness by inventing an owner or date. "Latest" requires a date/version check, not simply the first search result.

## Follow-up drafts

```text
For [defined contact set and period], review the accessible conversation and proposal records. Summarize each contact's status with source links. Separate stated reasons from possible explanations for silence. Draft a short reply in [supplied style]. Check names, amounts, and commitments against the records. Return drafts for review; sending requires separate authorization.
```

Silence does not establish the reason for non-response. Style examples can guide voice but cannot supply facts about another contact.

## Short factual rewrite

```text
Make the supplied [text] clearer for [audience]. Preserve [factual fields] exactly. Return [length and format]. Check the preserved fields against the original.
```

This task rarely needs a broad plan, multiple options, or repeated review cycles.

## Repository fix with incomplete context

```text
Fix [observed behavior] so [expected behavior]. Inspect the actual repository and reproduce the failure before choosing the cause. Treat [user theory] as a hypothesis. Keep the change within the affected behavior. Use the project's required checks and relevant regressions to verify the fix. Return the changes, evidence, and any checks you could not run.
```

Do not invent file paths or verification commands. Tests for state transitions or nearby behavior can justify several checks; the number is not fixed by the template.
